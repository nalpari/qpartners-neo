## 1. 배경

### 1.1 설계와 구현의 차이

| 항목 | 화면설계서 (v1.0_confirmed ~ v2.3 동일) | 현재 구현 |
|---|---|---|
| 기간 검색 조건 | **발송일** `yyyy.mm.dd ~ yyyy.mm.dd` | 등록일 `createdAt` (`src/app/api/admin/mass-mails/route.ts:383-390`) |
| 정렬 | 「최근 **발송** data를 상위에 표시」 | 등록일 내림차순 (`route.ts:397`) |
| 목록 첫 열 | 발송일 (「임시저장인 경우, 발송일 미표시」) | `sentAt` (`bulk-mail-table.tsx:96-97`) — 발송 완료 건만 값이 있음 |

- 기간 검색은 `5041def5`(2026-04-15)에서 처음 들어갔고, 주석은 「配信日 범위 검색」인데 조건은 `createdAt` 이었다. 이후 `058e98b7`(04-16)에서 타임존만 보정했고 기준 컬럼은 바뀐 적이 없다.
- 등록일을 기준으로 삼은 근거는 요구사항정의서·고객 개선요건·레포 설계 문서 어디에도 없다. `openapi.ts` 의 「등록일」 설명은 구현에 맞춰 쓴 내부 문서다.

### 1.2 날짜 형식 오류 — 현재 기간 검색 자체가 실패

- 화면은 `startDate`/`endDate` 를 `Date.toISOString()` (`2026-11-01T15:00:00.000Z`) 으로 보낸다 (`bulk-mail-search.tsx:57-58`).
- 서버는 `YYYY-MM-DD` 만 허용한다 (`src/lib/schemas/mass-mail.ts:22-29`).
- 개발서버 API 실측 (2026-11-16): ISO 형식 → **400** 「日付はYYYY-MM-DD形式で入力してください」, `YYYY-MM-DD` → 200.

## 2. 결정 사항 (2026-11-16 사용자 확정)

**기간 검색·정렬 기준일 = 발송일 → (없으면) 예약일 → (둘 다 없으면) 등록일** — 값 기준(상태 무관)

| 값 | 기준일 |
|---|---|
| `sentAt` 있음 | `sentAt` (발송일) |
| `sentAt` 없음, `scheduledSendAt` 있음 | `scheduledSendAt` (예약일) — 예약·예약에서 넘어간 대기/발송 중·예약일을 넣어 둔 임시저장 |
| 둘 다 없음 | `createdAt` (등록일) — 즉시 발송 대기/발송 중/실패, 예약일 없는 임시저장 |

- **검색·정렬 전용이다. 화면 표시는 바꾸지 않는다.**
  - 목록 「配信日」 열: `sentAt` 만, 없으면 「—」 — 설계서 「임시저장인 경우, 발송일 미표시」
  - 상세·수정 「配信日」 칸: `sentAt`, 없으면 등록일시 — 설계서 등록화면 ③ 「대량메일 등록 시, 등록일시 표시」
- 마지막 기준을 등록일로 둔 이유: 상세 화면이 설계서대로 「발송일 없으면 등록일시」를 보여 주므로, 검색 기준도 같은 날짜를 쓴다. (한때 갱신일 B안을 검토·구현했다가 같은 날 이 규칙으로 정정)
- **DB 변경 없음.** 비교는 **일자 단위**(JST).

## 4. 구현 방침

### 4.1 기간 검색 조건 (Prisma, raw SQL 불필요)

```ts
const range = { gte: startOfJstDay(startDate), lte: endOfJstDay(endDate) }; // 한쪽만 있으면 그쪽만
const deliveryDateWhere: Prisma.MassMailWhereInput = {
  OR: [
    { sentAt: { not: null, ...range } },
    { sentAt: null, scheduledSendAt: { not: null, ...range } },
    { sentAt: null, scheduledSendAt: null, createdAt: range },
  ],
};
```

- ⚠️ **기존 `where.OR` 와 충돌 주의.** 登録者 이름 검색(`route.ts:372-377`)이 이미 `where.OR` 를 쓴다.
  - 그대로 대입하면 덮어써진다.
  - `where.AND = [...]` 로 두 OR 를 묶는다.
- JST 경계 계산은 현 구현(`T00:00:00+09:00` / `T23:59:59.999+09:00`)을 유지한다.

### 4.2 정렬

- Prisma `orderBy` 는 `COALESCE`/`CASE` 식을 표현하지 못한다. 그래서 2단계로 조회한다.
  1. 조건에 맞는 행을 키 컬럼만(`id, sentAt, scheduledSendAt, createdAt`) 전부 조회한다.
  2. §2 규칙으로 `deliveryAt` 을 계산해 내림차순(동률 `id` 내림차순) 정렬한 뒤, 페이지 구간의 `id` 를 잘라낸다.
  3. 그 `id` 들로 상세(첨부·대상 포함)를 조회하고, 2의 순서로 다시 정렬한다.
- `totalCount` 는 1의 건수를 쓴다(count 쿼리 1회 절감).
- 대량메일은 발송 단위라 행 수가 작아서 전체 키 조회의 부담이 없다. 수천 건 규모가 되면 raw SQL(`ORDER BY COALESCE(...)`)로 바꾼다.

### 4.3 표시

- 「配信日」 열은 그대로 `sentAt` 만 표시한다(발송 완료 건만 날짜, 그 외 「—」). 기준일은 화면에 노출하지 않는다.
