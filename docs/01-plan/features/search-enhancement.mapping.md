### 3.1 좌측 필터 5축 (전부 신규)

`型番（製品一覧）` / `情報種別` / `製品カテゴリ` / `製品ステータス` / `資料種別`
근거: `01-search.html` `facet-head > h2`. `型番` 축은 제품일람 탭 표시 중에만 적용.

> 🔴 **체크 상태의 의미는 목업을 따르지 않는다 (2026-10-13, 계획서 §24).**
> 목업 `01-search.html:1360` `axisPass(set,value){return set.has(value)}` 는
> 「체크한 것만 조회 대상」이라 **전해제 시 0건**이지만, 우리 산출물
> `01_기능정의서.md` F-006 · `03_화면흐름도.md` S-1 5단계는
> 「**한 축 전체 해제 = 「필터 없음(전체)」**」로 확정하고 있다. **산출물 기준으로 구현했다.**
> - 체크가 하나도 없는 축 → 그 축은 조건이 아니다
> - 전부 체크 → 그 선택지들로 거른다 (「하나씩 켠 누적 = 전부 체크」가 일치)
> - 초기 상태 = **전 축 체크 해제**
>
> 그래서 목업의 사이드바 맨 아래 **「カテゴリをリセット」(`:508`) 버튼은 구현하지 않는다** —
> 목업에서 그 버튼은 「전부 체크 = 초기 상태로 복귀」였고, 상단 `すべて選択` 이 그 역할을 한다.
>
> 산출물 F-006 의 「**각 축의 건수를 재계산**」은 **미구현**이다 (계획서 §16 목업과 다른 점 2).

> 🔴🔴 **위 2026-10-13 모델은 2026-10-23 사용자 결정(계획서 §27.3)으로 교체되었다.**
> 아래가 현행 규칙이며, 윗 블록은 결정 이력으로만 남긴다.
>
> | 축 상태 | 취급 |
> |---|---|
> | 전부 체크 | 그 축이 **AND 조건 대상** |
> | 일부 체크 | 그 축이 **AND 조건 대상** (체크된 선택지 OR) |
> | **전부 해제** | 그 축만 **AND 조건에서 제외**. 조회에서 빠지는 것이 아니라 **결과가 넓어진다** |
>
> - **초기 상태 = 전 축 전부 체크** (10-13 의 「전 축 해제」를 뒤집음).
>   클라이언트 state 는 `facetCategoryIds: null`(미설정)이고, 화면은 전부 체크로 보이며,
>   **서버에도 전부 체크와 같은 조건이 나간다** — `contents-contents.tsx` 의 `facetParams` 가
>   `null` 을 각 축의 전체 id 로 펼친다. 그래서 `null` 과 `[]` 는 **서버 조건이 다르다.**
> - 전체 id 를 state 에 채우지 않는 이유: 축 데이터가 비동기로 와서 `useEffect` 안 setState 가
>   필요해지는데, React Compiler 규칙이 이를 금지한다.
> - 복귀 수단은 상단 `すべて選択`(= 미설정과 동일 조건), `すべて解除` 는 전 축을 조건에서 뺀다.
> - ⚠️ 조건이 걸린 축은 **그 축에 분류가 하나도 없는 자료를 탈락시킨다.** 개발 DB 에서 초기
>   화면이 2,459건이 아니라 21건으로 보이는 이유다(2026-10-26 실측) — 데이터 상태이며 구현
>   문제가 아니다.
> - 회귀 방어는 `scripts/e2e/search-facets.e2e.mjs` 6케이스가 담당한다.

## 9. 판단 필요 항목

Phase 3 에서 **새로 2건**이 올라왔다 — 둘 다 목업에 있고 현행·계획서에 없던 기능이다.
「목업대로 구현」 지시의 대상이지만 **사전 설계가 필요한 규모**라 제거/구현 판단으로 끝나지 않는다.
상세는 계획서 §13 마지막 표.

| # | 항목 | 판단이 필요한 이유 |
|---|---|---|
| 3 | 동의어·표기흔들림 보정 (`SYNONYMS` 35쌍 + `expandQuery`) | 사전을 코드 상수 / 공통코드 마스터 / 신규 테이블 어디에 둘지. 운영자 편집 화면까지 가면 별건 규모 |
| 4 | 검색어 정규화 (`norm()` — 하이픈·공백 제거 후 비교) | 콜레이션이 못 하는 부분이라 정규화 컬럼 추가 + 저장 시 동기화가 필요 |

아래 2건은 모두 종결됐다.

1. ~~**자료상세 `投稿対象` 패널** (발견 F) → 제거 확정~~ → **🔴 취소 (2026-10-12, Phase 7).**
   목업에 `掲載対象` 카드로 **존재한다**(`01-search.html:1694`, `docTargetCards` 가 게시대상별
   기간까지 렌더). 대응표를 만들 때 **neo 라벨 `投稿対象` 로 목업을 grep** 해 0건이 나온 것이
   원인이다. `ContentsDetailTarget` 유지. 상세는 계획서 §5 정정 블록
2. ~~`製品ステータス` 카드 추가 여부~~ → **철회.** 현행이 1Depth 를 동적 순회하므로 이미 자동 표시된다(§4). 현행 구현을 확인하지 않고 목업 카드 수만 세어 판단 항목으로 올린 오류였다
