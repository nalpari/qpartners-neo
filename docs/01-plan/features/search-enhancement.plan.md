## Executive Summary

| Perspective | Content |
|-------------|---------|
| **Problem** | 자료를 제품 모델번호로 찾을 수 없다. 카테고리는 2Depth 고정이라 "제품 카테고리 → 형번" 계층을 표현할 수 없고, 형번을 카테고리로 관리하려 해도 `/api/categories` 가 3Depth 를 거부한다. |
| **Solution** | 형번을 카테고리가 아닌 **별도 마스터 테이블**로 분리(`qp_product_models`)하고, 자료-형번을 N:M(`qp_content_product_models`)으로 연결한다. 카테고리에는 제품일람 노출 플래그(`is_product_list`) 1개만 추가한다. |
| **Function/UX Effect** | 사용자는 형번으로 자료를 검색하고 `제품일람` 탭에서 제품 단위로 자료를 모아 볼 수 있다. 관리자는 `型番管理` 화면에서 형번을 등록·표시순서·표시여부를 관리한다. |
| **Core Value** | 카테고리 스키마를 건드리지 않고 형번 축을 추가. 2Depth 제약·`isVisible` 1Depth 전용 제약과 간섭하지 않는다. |

### 2.2 화면별 신규/수정 구분 — 구현 대상 6곳

목업은 01 한 파일에 목록·자료상세·제품상세를 해시 라우팅(`#/doc/<id>`, `#/product/<id>`)으로 담았지만,
현행은 상세가 별도 라우트(`/contents/[id]`)다. 따라서 목업 화면 수(4) ≠ 구현 대상 수(6).

| 목업 | 구현 대상 | 성격 | 내용 |
|---|---|---|---|
| 01 목록 | `/contents` (`contents-contents.tsx`, `contents-search.tsx`, `contents-table.tsx`) | **대체·확장** | 현행 ag-grid 9컬럼을 전부 포함하고 분류 4축 컬럼 추가 + 좌측 사이드바 5축 + `제품일람` 탭 신설 |
| 01 자료상세 | `/contents/[id]` (`contents-detail-category.tsx` 등) | **수정** | `紐づく型番` 패널 추가 |
| 01 제품상세 | **신규 라우트** | **신규** | REQ-010 — 그 제품에 紐づく 자료 목록. 현행에 제품 라우트 없음 |
| 02 등록·수정 | `contents-form.tsx` | **수정 1곳** | `紐づく型番` 섹션 추가. `/contents/create` 와 `/contents/[id]/edit` 가 `ContentsForm` 을 `mode` prop 으로 공유하므로 수정 지점은 하나 |
| 03 형번관리 | `/admin/product-models` | **신규** | 화면 + 메뉴 + RBAC |
| 04 카테고리관리 | `/admin/categories` | **수정** | `製品一覧表示` 1필드 추가 |

**제품상세 라우트 경로**: `/products/[id]` (최상위).
`/contents/products/[id]` 는 기존 `/contents/[id]` 와 같은 깊이에 static·dynamic 세그먼트가 공존하는 형태인데,
번들된 Next.js 문서(`node_modules/next/dist/docs`)에 static/dynamic 우선순위 규칙이 명시돼 있지 않아
동작을 문서로 확정할 수 없다. 충돌 소지가 없는 최상위 경로를 택한다.
메뉴·RBAC 상으로는 `CONTENT` 매트릭스를 그대로 사용한다(제품상세는 콘텐츠 열람의 일부).

### 2.3 신설이 필요한 API — 현행에 없음 확인

## 3. Implementation Plan

### Phase 1: DB 스키마
- `qp_product_models` — `category_id` FK(`qp_categories`), `model_code`, `sort_order`, `is_visible`, 감사 컬럼
- `qp_content_product_models` — `content_id` + `product_model_id` 복합 PK
- `qp_categories.is_product_list` BOOLEAN DEFAULT false
- 유니크 제약: `(category_id, model_code)` — §4 비교 규칙 참조
- **개발 DB 적용은 별도 승인 후** (공유 스키마 변경)

### Phase 2: 메뉴 · RBAC
동기화 5곳 — 하나라도 빠지면 탭이 조용히 사라진다.

| 대상 | 내용 |
|---|---|
| `src/lib/schemas/common.ts` | `menuCodeValues` 에 `"ADM_PRODUCT_MODEL"` |
| `src/lib/menu-codes.ts` | `ADMIN_MENU.PRODUCT_MODEL` |

### Phase 3: API
- 형번 CRUD (`/api/product-models`) — 목록·등록·수정·삭제, 중복 체크(저장 전 `trim()`)
- 카테고리 `is_product_list` 수정 반영
- 콘텐츠 저장 시 형번 연결(N:M)
- `/api/contents` 검색 확장 — **검색 대상에 형번 추가**(`qp_product_models.model_code` 경유), **본문 제외**

- 제품일람 집계 엔드포인트 **신설**

### Phase 4: 03 형번관리 (신규 화면)
목록 + 등록/편집 폼. 행 클릭 = 편집 진입, 형번명 3자 이상 검색 게이트.

### Phase 5: 04 카테고리관리 (수정)
`製品一覧表示` 필드 추가. 전 카테고리 대상(2Depth 한정).

### Phase 6: 01 목록 (대체·확장)
좌측 사이드바 5축, `자료일람`/`제품일람` 2탭. `詳細条件` 패널과 그 안의 필터 4종은 제거(§5).

### Phase 7: 자료 상세 (수정) · 제품 상세 (신규)

`紐づく型番` 섹션 — 복수 선택, 비표시 형번도 선택 가능(REQ-007 방침2). `ContentsForm` 1곳 수정으로 create/edit 양쪽 반영.

### Phase 9: 통합 확인
린트·타입·빌드 체크. 시나리오 확인(카테고리 제품일람 ON → 형번 등록 → 콘텐츠 연결 → 검색 반영 → 제품상세 진입).

## 4. Technical Decisions

| 항목 | 결정 | 근거 |
|---|---|---|
| 형번 관리 방식 | 카테고리가 아닌 **별도 마스터 테이블** | `/api/categories/route.ts:123` 3Depth 거부, 동 `:105-108` `isVisible` 1Depth 전용 → REQ-007 형번별 미표시 불가. 카테고리끼리 연결 구조가 없어 제품 상태를 형번에 붙일 수 없음 |
| 제품일람 적용 범위 | **전 카테고리** (2Depth 한정) | 고객 확장성 요구(10/8 리뷰). 목업 `productListCategories()` 가 `!c.isParent && c.isProductList` — parent 조건 없음 |
| 형번 중복 비교 | 동일 카테고리 내. **대소문자 무시 + 앞뒤 공백 제거, 가운데 공백 보존** | 가운데까지 제거하면 `栄信 SRシリーズ` 와 `栄信SRシリーズ` 가 중복 처리되어 다른 형번이 막힌다. DB 콜레이션은 마이그레이션 시 조회해 확인하고 `_ci` 가 아니면 애플리케이션에서 보정 |
| 표시순서 | 중복 허용, 동일 시 형번명 昇順 | 10/8 리뷰 결정 |
| menuCode | `ADM_PRODUCT_MODEL` / `型番管理` / `/admin/product-models` / `sortOrder: 8` | 기존 `ADM_*` 패턴. sortOrder 는 맨 뒤 — 기존 3행 UPDATE 를 피한다(운영자가 메뉴관리에서 조정해둘 수 있음). 실제 이행 시 탭 위치 조정 |
| 권한 | SUPER_ADMIN·ADMIN 만 CRUD | `ADMIN_FULL_MENUS` 에 코드 추가하면 `buildPermissions()` 가 자동 산출. 비관리자 4역할은 `GENERAL_MENUS` 밖이라 전부 false |
| 디자인 | **목업이 아니라 neo 토큰 값을 따른다** | 목업이 신규 컴포넌트 9곳에서 토큰을 우회해 근사색·근사치수를 하드코딩. 상세는 메모리 `project-mockup-1607-design-deviations` |
| 용어 | `掲示対象` 현행 표기 유지 | 목업의 `掲載対象` 는 따르지 않음 |

### ⚠️ 정정 — 키워드 `AND`/`OR` 는 제거 대상이 아니다 (2026-10-12, Phase 3)

v1.0 의 제거 5번 항목에 들어 있던 키워드 `AND`/`OR` 는 **목업에 존재한다.** `詳細条件` 패널에서
**검색바 안으로 옮겨진 것**이지 없어진 것이 아니다.

- 근거: `01-search.html:515` `<select id="keywordMode"><option value="AND"><option value="OR">`
  (검색 입력창 왼쪽, 폭 94px) + `:1084` `scoreDoc()` 이 그 값으로 토큰 결합을 분기
- 제거 5번은 `社内会員の掲示のみ表示`(internalOnly) **하나만** 남는다 → 제거 대상은 **6건 그대로**(①~⑥)이나
  ⑤의 범위가 절반으로 줄어든다
- 영향: `keywordOp` 파라미터와 서버 결합 로직은 **유지**한다(Phase 3 반영 완료). Phase 6 에서 UI 를
  `詳細条件` 패널이 아니라 **검색바**에 배치한다

v1.0 작성 시 `詳細条件` 패널 내부 요소를 패널째로 제거 목록에 넣으면서 같이 쓸려 들어간 오류다.

### 🔴 정정 — 자료상세 `投稿対象` 패널은 제거 대상이 아니다 (2026-10-12, Phase 7)

v1.0 의 제거 ⑥(대응표 발견 F)은 **오판이었다. 목업 자료상세에 그 패널이 있다.**

- 근거: `01-search.html:1694`
  `<section class="doc-admin-card doc-target-card"><div class="doc-target-label">掲載対象</div>…`
  + `:1625` `docTargetCards(d)` 가 **게시대상별로 `시작～종료` 기간을 함께** 렌더한다.
  현행 `ContentsDetailTarget` 과 **기능이 동일**하다
- 오판 사유: 대응표를 만들 때 **neo 라벨 `投稿対象` 로 목업을 검색**해 0건이 나왔다.
  목업은 같은 것을 `掲載対象` 으로 쓴다 — 표기만 다르다
- → **`ContentsDetailTarget` 유지.** 제거 목록은 6건 → **5건**
- 노출 조건은 **현행 유지**(사내 사용자 전용, `isInternal &&`). 목업은 권한 분기가 없는
  데모라 무조건 렌더하지만, 게시대상·기간은 운영 메타정보다
- 라벨도 현행 `投稿対象` 유지 — 목업의 `掲載対象` 는 따르지 않는다(§4 용어 정책과 동일)

**⑤(키워드 AND/OR)과 같은 유형의 오류가 두 번 나왔다** — 둘 다 「라벨 문자열로 목업을 grep 해서
0건 → 목업에 없음」 으로 단정한 것이다. 대응표의 「목업에 없음」 판정은 **기능 단위로 다시 확인**해야
한다(라벨 표기가 다를 수 있다).

**복구 가능하게 둔다**: 화면(UI)만 제거하고 `listContentsQuerySchema` 파라미터와 서버 필터 로직은 **삭제하지 않는다.** 되살릴 때 UI 만 다시 붙이면 되도록.

**영향 확인 완료**: `roleCode`/`department` 를 쓰는 다른 코드는 전부 콘텐츠 등록 폼(`contents-form-post-target.tsx` 게시대상, `contents-form-management.tsx` 담당부문)이며 목록 검색과 별개 용도다. 목록 검색 파라미터 소비처는 `contents-search.tsx` 단독이고, 홈 검색바는 `keyword` 만 전달한다.

|---|---|---|
| 사전 없이 이미 검색된다 | **15** | 키가 정식명칭에 그대로 들어 있어 `contains` 부분일치로 걸린다 (`説明書`→`取扱説明書`, `点検`→`点検・アフターサービス` 등) |
| 자동완성이 흡수한다 | **3** | 앞 2자가 공통이라 그만큼만 쳐도 후보가 뜬다 (`蓄電池`→`蓄電システム`, `パワコン`→`パワーコンディショナ`, `太陽光パネル`→`太陽電池モジュール`) |
| 사전이 없으면 0건 | **21** | 완전히 다른 현장 통용어 (`バッテリー`, `パネル`, `メンテ`, `取説`, `工事`, `お知らせ`, `ヘムス` 등) |

실익은 **21쌍**이고, 0건을 본 이용자는 좌측 카테고리 필터로 찾아갈 수 있다 — 검색이 유일한 경로가 아니다.
요구사항정의서 REQ-001~010 에도 항목이 없어 **범위 제외**로 확정했다. 넣는다면 21쌍 고정 사전이므로
코드 상수가 적절하다(제품 라인업이 바뀌지 않는 한 늘어나지 않는다). 공통코드 마스터·전용 테이블은
「단어가 계속 늘어난다」는 전제를 깔 때만 성립하고, 그 전제는 위 분류로 깨졌다.

**검색어 정규화** — 현 구현은 `tokenizeKeyword`(공백 토큰 분리) → 필드별 `contains` 2단이고,
콜레이션 `utf8mb4_unicode_ci` 가 대소문자·전각반각을 흡수한다. 실측:

| 입력 | 현재 |
|---|---|
| `hqjp` | ✅ (부분일치 — 앞부분만 쳐도 걸린다) |
| `hqjp-a44-1` | ✅ |
| `ＨＱＪＰ-Ａ44-1` | ✅ (콜레이션) |
| `HQJP A44 1` | ✅ (토큰 3개가 각각 부분일치) |
| `hqjpa441` | ❌ |

못 찾는 것은 **구분자를 전부 빼고 붙여 쓴 1가지**뿐이고, 그렇게 치는 이용자도 `hqjp` 까지만 치면
자동완성에 형번이 뜬다. 정규화 컬럼 추가 + 저장 시 동기화는 이 한 가지를 위한 작업이라 **범위 제외**.

| | 목업의 두 지점 |
|---|---|

**전 카테고리(모든 2Depth)로 구현했다.** 근거:
1. 계획서 §4 확정사항이 전 카테고리이며 **고객 확장성 요구의 결과**다. 제품 카테고리 한정은

2. 목업의 데이터 레이어도 축 제한이 없다 — 04 폼의 제한은 `TREE2STORE` 하드코딩에 의존하는

   운영자가 관리한다 — 코드 하드코딩은 금지 패턴이다
4. 전 카테고리로 열어도 **기본값이 N 이라 동작 변화가 없다**. 제품한정이 맞다면 운영자가 안 켜면
   되지만, 반대로 막아 두면 고객 요구를 못 지키고 되돌리려면 또 번복이 된다 (§8 리스크 참조 — 이미 3번 뒤집힌 항목)

### 설계 결정 2건

1. **`製品一覧表示` 는 값이 바뀐 경우에만 PUT 에 담는다.**

   저장했을 때도 전파가 일어나 개별로 켜 둔 자식 설정이 통째로 덮인다.** 비교 기준은 폼 초기값과
   같은 파생값이라 "화면에 보인 값과 다를 때만" 전송된다.
2. **전파는 양방향**(Y·N 모두). `isInternalOnly` 전파는 노출 범위를 좁히는 Y 방향만인데
   (되돌릴 때 자식 설정 보존), 이쪽은 「전체 선택」 체크박스라 해제도 전체에 적용돼야
   조작과 결과가 일치한다.

## 26. 콘텐츠 축별 필수 분류 — 2026-10-14

### 왜 필요했나

좌측영역이 「체크된 축만 조건」으로 바뀌면서(§24), **분류가 비어 있는 자료는 그 축을 쓰는 순간
결과에서 사라진다.** 그런데 등록 검증이 「전체에서 1개 이상」이었다.

```
"カテゴリを1つ以上選択してください。"   // contents-form.tsx (종전)
```

`製品分類` 만 고르고 저장하면 `情報種別`·`製品ステータス` 가 빈 자료가 만들어진다.
**누락이 쌓인 원인이 이것**이고, 기존 누락분을 채워도 새 자료에서 다시 생긴다. 입구를 막았다.

더 나쁜 것은 **서버에 카테고리 검증이 아예 없었다**는 점이다 — 실측으로 `categoryIds: []` 가
HTTP 201 로 통과했다. 화면만 막혀 있었다.

### 규칙

`情報種別` · `製品分類` · `製品ステータス` 를 **각각 1개 이상** 필수.
단 **현재 표시 중인 축에만 적용**한다(`isActive && isVisible`).

### 축 코드를 상수로 둔 이유

`PRIORITY_CATEGORY_ORDER` 폐기 이후 「축 코드를 코드에 박지 않는다」를 지켜 왔지만,
여기서는 상수로 둔다. 그 원칙이 막으려던 실패는 **「폐지된 축을 상수가 참조한 채 조용히
어긋나는 것」**인데, 여기서는 표시 중인 축에만 적용하므로 축이 폐지되면 요구가 자동으로 빠진다.
TO-BE 개명(`製品分類`→`製品カテゴリ`)은 **표시명만** 바뀌고 `categoryCode` 는 유지되므로 영향 없다.

> 처음에는 카테고리에 `is_required` 컬럼을 추가하자고 제안했으나, **사용자 지적대로 과한 설계**였다.
> 검증만 넣으면 되는 일이었다.

### 구현

| 파일 | 내용 |
|---|---|
| `lib/schemas/common.ts` | `REQUIRED_AXIS_CODES = ["INFO","PROD","PRDST"]`. **prisma 비의존 모듈에 둔다** — 클라이언트 컴포넌트가 import 하므로 |
| `lib/content-required-axes.ts` | **신규** — `findMissingRequiredAxes()` / `missingAxesMessage()`. 표시 중인 축만 조회해 판정 |

| `api/contents/[id]/route.ts` (PUT) | **`categoryIds` 를 보낸 경우에만** 판정 — 미지정은 「변경 의도 없음」이라 막으면 기존 자료를 고칠 수 없다 |
| `contents-form.tsx` | 축별 판정으로 교체. 안내 문구는 비어 있는 축 이름을 그대로 넣는다 |

### 검증

| | 종전 | 지금 |
|---|---|---|
| 1Depth → Y | 하위 전체 Y | 동일 |

### 추가 수정 — 1Depth 사내전용 괴리 (2026-10-30, 커밋 `331e8cf6`)

제외 목록에 넣었던 건을 사용자 판단으로 **머지 전 수정**으로 올렸다. 배포 후 카테고리 표시

**증상** — 1Depth 를 `社内会員専用` Y 로 켠 뒤 그 아래 2Depth 하나를 N 으로 되돌리면:

| | DB | 화면 | 비사내 사용자에게 |
|---|---|---|---|
| 1Depth | **Y 유지** | N (자식에서 파생) | — |
| 2Depth(N 으로 바꾼 것) | N | N | **안 보임** |
| 축 전체 | — | — | **사라짐** |

**원인** — 노출 판정(`category-tree.ts:144`)이 부모를 먼저 보고 부모가 Y 면 자식 값과 무관하게
축 전체를 숨긴다(축 제목이 1Depth 이름이라 자식만 내보내면 사내 분류명이 드러난다 — 이 동작
자체는 의도대로다). 여기에 ① 1Depth 표시값을 자식에서 파생(`resolveInternalOnlyValue`)하고
② 폼이 「파생값과 다를 때만 전송」하는 두 가지가 겹쳐, 화면은 N 으로 보이는데 되돌릴 수단이
없는 상태가 됐다(Y 저장 → N 저장으로 전체 전파를 두 번 돌려야 하고 개별 자식 설정이 날아간다).

**수정(A안)** — 2Depth 를 N 으로 저장할 때 부모가 Y 면 **부모도 함께 N 으로 내린다.** 형제는
건드리지 않으므로 각자 Y 면 그대로 숨겨지고, 조작한 그 2Depth 하나만 공개된다. 화면 표시값과
DB 가 일치하게 되어 되돌릴 필요 자체가 없어진다. 노출 범위를 **넓히는** 변경이라 감사 로그
(`사내전용 부모 해제`)를 남긴다.

⚠️ **기존 데이터는 자동으로 풀리지 않는다.** 이미 「부모 Y + 자식 N」 인 행이 있으면 그 2Depth 를
한 번 다시 저장해야 해소된다.
